# Окно Ripster.exe — это WebView2, а не браузер

Пользователи запускают Ripster двумя разными оболочками, и они **ведут себя
по-разному**:

- `Ripster.exe` → pywebview + **Edge WebView2** (окно-приложение) — то, что
  ставит установщик и чем пользуется большинство;
- `Ripster (browser).cmd` → обычный Chrome/Edge/Yandex — запасной ярлык.

Один и тот же билд может работать во втором и быть полностью сломанным в первом.
Это уже случалось дважды, и оба раза диагноз ушёл не туда, потому что «у меня
всё работает» проверялось в браузере.

## Что в WebView2 молча не работает

### `window.open()` возвращает `null` (проверено 27.07.2026)

WebView2 без обработчика `NewWindowRequested` **не открывает попапы вообще**.
Возвращается `null` — ровно то же, что при блокировке попапов пользователем,
поэтому фронт честно писал «Popup заблокирован браузером — разреши попапы»,
а разрешать было нечего.

Симптом был у двух пользователей за час: у первого — эта надпись, у второго —
`ERR_CONNECTION_REFUSED` на `127.0.0.1:4381` при ручном открытии ссылки входа,
потому что ветка «попап не открылся» ещё и звала `login-cancel`, а тот убивал
helper, слушавший этот порт. Две разные с виду жалобы = одна причина.

**Правило: никакого OAuth/внешнего входа через `window.open` без запасного пути.**
Схема, применённая для Spotify (`orpheus_ui.js` + `/api/orpheus/login-open`):

```js
const popup = window.open(url, 'name', 'width=520,height=700');
if (!popup) {
  const opened = await api('POST', '/api/<flow>/login-open');  // сервер откроет системный браузер
  if (!opened?.ok) { /* только теперь это реально «попапы запрещены» */ }
  // ВАЖНО: helper НЕ отменять — колбэк всё ещё придёт
}
```

Серверная сторона обязана быть узкой:

- открывает **только URL, который сам сгенерировал** (хранится в глобале
  модуля), никогда не тот, что прислал клиент — иначе это «открой что угодно
  на машине хозяина»;
- только при `request.client.host in ("127.0.0.1", "::1", "localhost")` —
  через туннель браузер хозяина открывать нельзя;
- `webbrowser.open` в `asyncio.to_thread`, запасной путь `os.startfile`.

Флоу должен переживать отсутствие хэндла попапа: следить за завершением через
WebSocket-событие (`orpheus_authed`), а не через `popup.closed`.

### `fetch()` к 127.0.0.1 со splash-страницы

Страница, созданная как `webview.create_window(html=...)`, имеет
`null`-origin, и Chromium режет её запросы к приватной сети — **и обычный fetch,
и `mode:'no-cors'`**. Подробности и правильный паттерн (опрос из Python +
`load_url`) — в скилле `build-ripster-launcher` и
[[project_launcher_splash_cors_gotcha]].

## Как проверять перед релизом

Минимальный чек-лист для любой фичи, которая открывает окно, качает файл или
трогает буфер обмена:

1. Прогнать её в **`Ripster.exe`**, а не только в браузере. Если фича трогает
   `window.open`, `window.showSaveFilePicker`, `navigator.clipboard`,
   `<a download>` или скачивание — считать её подозрительной по умолчанию.
2. Логику серверной части — юнит-тестом с подменённым `webbrowser.open`
   (никаких реально открывающихся окон, хозяин часто в игре и фокус красть
   нельзя):
   ```python
   import ripster.routes.setup as S
   webbrowser.open = lambda u, *a, **k: opened.append(u) or True
   await S.orpheus_login_open(Req('192.0.2.55'))   # должен отбить
   await S.orpheus_login_open(Req('127.0.0.1'))      # должен открыть
   ```
3. Живой сервер: убедиться, что вспомогательный процесс реально слушает свой
   порт (`socket.connect(('127.0.0.1', 4381))`) **и** что отмена его гасит —
   так ловится «connection refused», который выглядит как проблема сети.

## Диагностический признак

**«Из батника работает, из ярлыка/exe — нет»** = почти наверняка ограничение
WebView2, а не баг логики. Первым делом спрашивать пользователя, чем именно он
запускал: скриншот окна с рамкой Ripster и скриншот вкладки браузера выглядят
похоже, но это разные среды.

## 🔴 «Я всё исправил, а не применяется» = старый JS из кэша WebView2

Окно Ripster.exe кэширует `index.html` и ассеты АГРЕССИВНО. Правка `static/js/*.js`
или `.html` НЕ доходит до пользователя, пока окно не перезагружено ЖЁСТКО
(Ctrl+Shift+R или закрыть-открыть окно). Это самый частый ложный «фикс не сработал»
(02.08.2026 — так было и с gapless, и с обложками, и со статистикой подряд).

Правило на каждую правку фронта:
1. Подними версию в теге: `static/index.html` → `…/foo.js?v=N` (и в зеркале
   `github_setup/static/index.html`). Без бампа даже hard-reload может взять старое.
2. Отзеркаль файл в `github_setup/`.
3. Скажи владельцу перезагрузить окно жёстко. Питон не трогал → рестарт app.py НЕ
   нужен, сервер уже отдаёт свежий файл; ждём только клиент.
Проверять свою правку — только с `Network.setCacheDisabled(true)` в headless
(см. `ripster-headless-verify`), иначе тестируешь тот же кэш.

Связано: [[project_launcher_splash_cors_gotcha]], скилл `build-ripster-launcher`
(сборка и тестирование самого exe), `ripster-frontend-file-drift`.
