# Ripster живёт на машине пользователя. Ведите себя соответственно

Две поломки одного корня: мы вели себя как сайт, а работаем как программа.

## Правило 1. Функциональный ресурс лежит локально, а не на CDN

**01.08.2026: «сломался проигрыватель BBC».** Бэкенд был исправен целиком —
`/api/bbc/brands` → `/api/bbc/episodes` → подписанный HLS отдавались за
миллисекунды. Не работал фронт: `hls.js` грузился с `cdn.jsdelivr.net`, а у
машины в тот момент падало разрешение имён (в логе рядом
`getaddrinfo failed` для apresolve.spotify.com и пляшущий туннель). Без `Hls`
плеер молча проваливался в ветку «браузер не умеет HLS».

Диагностический признак: **бэкенд отдаёт данные, а фронт «не работает»** —
первым делом проверь внешние `<script src>`/`<link href>` в `static/index.html`.

Правило: всё, без чего фича не работает, лежит в `static/vendor/` и ставится
локально. Шрифты с Google Fonts допустимы — их отсутствие косметическое,
подставится системный.

```powershell
# положить и в корень, и в зеркало — установщик собирает github_setup/
Invoke-WebRequest <url> -OutFile static\vendor\<файл>
Copy-Item static\vendor\<файл> github_setup\static\vendor\<файл>
```

`ripster.iss` тянет `{#SrcDir}\*` рекурсивно, так что `static/vendor/` попадает
в установщик сам — отдельная строка в `[Files]` не нужна.

Проверять живьём, а не глазами: подними страницу в headless Chrome и убедись,
что `typeof Hls === 'function'` и звук реально пошёл (`currentTime > 0`,
`paused === false`) — см. скилл `ripster-headless-verify`.

## Правило 2. Состояние пользователя хранится на сервере, а не в localStorage

**01.08.2026: «жму добавить в избранное не первый раз, Ripster не помнит».**
Звезда на карточке радара писалась в `localStorage`. У Ripster минимум ДВЕ
оболочки — окно программы (WebView2) и запасной ярлык в браузере — и у каждой
свой профиль, а значит свой список. Плюс любая чистка данных сайта стирала
избранное молча.

Правило: всё, что человек осознанно отметил (избранное, вишлист, вкусы,
скрытые находки), едет на сервер — один список на всю программу, переживает
перезапуск, смену оболочки и переустановку браузера.

Рабочая схема (`/api/rel-favs` в `ripster/routes/radar.py`):

* `GET` — отдать список;
* `POST {uid, item, remove}` — добавить/снять;
* `POST {merge: true, items}` — **однократная переливка** того, что осталось в
  localStorage от прежних версий; слияние по ключу, ничего не затирает;
* локальная копия остаётся как мгновенный отклик и запасной путь: ответ сервера
  не ждём, ошибку глотаем, карточка перерисовывается сразу.

Ключ записи считают обе стороны — считайте его **одинаково**, иначе списки
разъедутся (`_fav_uid` на сервере повторяет `_relUID` на клиенте).

В localStorage остаётся только то, что и должно быть машинно-локальным:
раскладка фильтров, выбранная вкладка, «что уже видел» на этом экране.

## Проверка

```bash
python tools/test_radar_persistence.py          # склад радара
node <scratch>/bbcplay.js <session-cookie>      # BBC реально играет
```
Для серверного состояния — цикл «добавил → прочитал → дубль не создался →
слияние добавило только новое → снял → прибрал за собой».
