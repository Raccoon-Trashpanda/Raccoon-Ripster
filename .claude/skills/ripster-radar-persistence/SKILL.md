# Радар не имеет права терять найденное

Жалоба владельца звучит всегда одинаково — «видел карточку, потом она исчезла»
— а причин у неё несколько, и все они разные. Общее у них одно: **склад релизов
и лента строятся по РАЗНЫМ спискам**, и рассинхрон между ними прячет данные,
которые никуда не делись.

## Три места, где это ломается

### 1. Пере-обход артиста заменяет его релизы целиком

`_run_sp_scan` присваивает `_sp_artist_state[aid] = {"releases": rels, …}`, где
`rels` — свежая дискография. Всё, что пришло НЕ из дискографии, при этом
исчезает. Таких источников три, и каждый надо переносить руками
(`_carry_over`):

| источник | признак | почему дискография его не вернёт |
|---|---|---|
| полка/сборники | `alb_artist` | артист там не альбомный |
| живая лента «Что нового» | `live` | отдаёт релиз в минуту выхода; ремикс на чужом релизе в дискографию не попадёт вовсе |
| самопроверка склада | `recovered` | иначе пере-обход выкинет, самопроверка вернёт — и запись вечно мигает |

01.08.2026 условие проверяло только `alb_artist`, и **все 337 находок ленты**
стирались при первом же пере-обходе артиста.

### 2. Оборвавшаяся пагинация усекает список подписок

`_build_feed` перебирает ТОЛЬКО тех, кто есть в `_sp_followed_cache`. Проход по
`/v1/me/following` выходит по `break` на 429/401/не-200/исключении — и раньше
собранное подмножество заменяло полный список и уходило на диск. Обрыв на
2000-м из 5761 = минус две трети радара, навсегда.

Правило (`_merge_followed`): **заменять список целиком можно ТОЛЬКО после полной
пагинации.** Оборвалась — лишь добавляем новых, ничего не убирая. Флаг
`paged_ok` снимается в КАЖДОЙ ветке выхода по ошибке.

### 3. Потеря по любой другой причине

Ловить каждую причину отдельно — бесконечная работа, и каждый промах оплачивает
пользователь пропавшей карточкой. Поэтому на старте работает
`_reconcile_from_cache()`: `spotify_releases_cache.json` хранит СНИМКИ уже
отданных лент — то, что человек видел на экране. Чего склад не помнит, а снимок
помнит, возвращается с пометкой `recovered`. На боевых данных вернуло 160
релизов.

Границы намеренные: только окно хранения, только артисты, уже известные складу
(иначе снимок протащит обратно тех, от кого отписались).

## Перед правкой — прогнать тест

```bash
python tools/test_radar_persistence.py
```

Он проверяет обе чистые функции (`_carry_over`, `_merge_followed`) на всех
ветках. Меняешь правила переноса или обновления подписок — сначала добавь случай
в тест.

## Чего НЕ делать

* **Не «чинить» пропажу ручной подсадкой релиза.** Владелец прямо сказал: радар
  должен работать без вмешательства, иначе пользователи будут терять контент
  постоянно. Любая находка тут — повод на самолечение, а не на разовую заплатку.
* **Не путать «нет в радаре» с «потерялось».** Сначала спроси сам Spotify
  (api-partner `queryArtistDiscographyAll` + `queryWhatsNewFeed`, см. скилл
  `ripster-spotify-tokens`). 01.08.2026 «пропавший сегодняшний релиз PROFF»
  оказался несуществующим: у Spotify свежайший релиз артиста был двухмесячной
  давности, а скачанный владельцем `Days Of Thunder (Incl. PROFF Pres.
  Soultorque Remix)` издан **2016-08-01** — совпали день и месяц.
* **Не кэшировать пустой ответ надолго.** Это отдельный класс той же беды (см.
  `_TTL_EMPTY` в `digs_similar.py`: один 503 записывал «похожих нет» на месяц).
