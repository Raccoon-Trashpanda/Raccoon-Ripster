# Бесшовный плеер Ripster (Web Audio)

Истинный gapless в Ripster делает **отдельный движок `_WA`** в `static/js/player.js`
(включён настройкой `player-gapless`, по умолчанию on). Он НЕ через `<audio>` (там
смена `src` всегда даёт стык), а через Web Audio: следующий трек декодируется в
`AudioBuffer` заранее и запускается **на аудио-часах** ровно в конец текущего
(`src.start(endAt)`), а не в JS-колбэке `onended` (тот опаздывает на ~20мс). Дубль-
`<audio>` для этого пробовали и ОТКАЗАЛИСЬ — второй звуковой элемент двоил звук.

## Почему стык то есть, то нет — три звена, все обязательны

1. **`_waCanPlay(item)` — гейт по ДЛИТЕЛЬНОСТИ.** Для Deezer/SoundCloud gapless
   включается только если у трека известна `duration` И она ≤ 12 мин (декод целого
   FLAC у длинного микса — минуты). **Если `duration` не пришла в элемент очереди —
   `!dur` → gapless молча выключается, играет `<audio>` со стыком.** Значит любая
   сборка очереди (`playRelease` в sc_tab.js, `_buildAlbumStreamQueue` в
   player_lib.js, радио digs_radio) ОБЯЗАНА класть `duration` в каждый элемент.
   Это была реальная причина «5-секундных стыков» 02.08.2026 — очередь не несла duration.

2. **Предзагрузка — LOOK-AHEAD на несколько треков, а не на один.** У DJ-микса
   после длинного трека идёт сегмент на 37с, а декод FLAC под троттлингом Deezer =
   20–40с — один сосед не успевает. `_waPreloadAhead()` держит горизонт
   `_WA_LOOKAHEAD` (3) треков в `_WA.ahead` (Map idx→AudioBuffer), **ПОСЛЕДОВАТЕЛЬНО**
   (параллельные запросы Deezer троттлит ещё сильнее) и с ретраями.
   - **Таймаут обязателен.** `_waLoadBuffer(url, 25000)` использует AbortController:
     Deezer под рейт-лимитом держит соединение открытым, `arrayBuffer()` не
     завершается никогда → без abort вся последовательная цепочка виснет,
     `_WA._aheadRunning` застревает в `true`, дозагрузка мертва (поймано 02.08 —
     кэш пустой после 3 мин, при том что одиночный `_waLoadBuffer` работал).
   - Тик (250мс) дозаполняет горизонт и планирует стык, когда буфер готов.
   - Прунить прошлое (`_waPruneAhead`) — 48 декодированных FLAC (~30МБ PCM каждый)
     иначе съедят память.

3. **Планировщик стыка (`_waScheduleNext`)** ставит следующий источник на `endAt` =
   `(curStartT + curOffset) + (curBuffer.duration - curOffset) / rate`. Гейт:
   `if (endAt <= ctx.currentTime) return` (не в прошлое).

## 🔴 «Каша, фоном пошёл другой трек» — ДВА независимых класса, оба про ЛИШНИЙ источник

Инвариант: **в любой момент играет РОВНО ОДИН источник** (`curSource`) плюс, может,
один запланированный (`schedSource`), который стартует ровно в конец текущего. Двойной
трек = этот инвариант нарушен. Две причины (02.08.2026, обе чинены):

**A. Ручной скип (⏭) при уже запланированном стыке.** `_waPlay(idx)` гасил только
`curSource`, а `schedSource` оставался и стартовал параллельно с новым треком.
**Фикс:** `_waPlay` в начале зовёт `_waCancelScheduled()` — любой ЯВНЫЙ старт трека
сперва снимает стык. То же правило для любой новой точки входа в воспроизведение.

**B. Гонка в окне `await ctx.resume()` внутри `_waSeek`.** Между отменой стыка и
обновлением `curStartT` есть `await`; 250мс-тик успевал запланировать источник со
СТАРЫМ таймингом → он стартовал не в тот момент → наложение. **Фикс:** флаг
`_WA._seeking` (true на время перестройки seek), `_waScheduleNext` возвращается при
нём, а перед re-aim в конце seek — повторный `_waCancelScheduled()` (гасит то, что
проскочило в окне await).

**Правило на будущее:** добавляешь НОВЫЙ вызов `_waScheduleNext` или новую точку,
создающую BufferSource, — сначала спроси: «а что если стык уже запланирован / идёт
seek / промоушен?». Любой источник, кроме одного текущего и одного запланированного,
— это каша. Больше вызовов планировщика = больше гонок; добавляй их скупо.

## Как проверять (headless, см. `ripster-headless-verify`)
- `_waCanPlay(Preview.queue[0])` → true (иначе `<audio>`-стык).
- `_WA.curSource` не null (WA реально играет, а не `<audio>`).
- Дождаться `_WA.ahead.size >= 2` — горизонт заполняется (кэш look-ahead).
- Симулировать скип `_waPlay(5,0)` при живом `schedSource` → старый `schedIdx`
  должен СНЯТЬСЯ (не остаться 1). Это и есть тест на «двойной трек».
- Стык на слух headless НЕ ловит — финальное подтверждение всегда за владельцем.

## Кросс-сервисный LOSSLESS prefetch (для коротких Deezer-миксов, 02.08.2026)

Проблема: Deezer сам себя троттлит, когда играющий поток и предзагрузка идут через
ОДИН аккаунт. На DJ-миксе с коротким первым треком (fabric: трек1=46с) следующий не
успевает скачаться → яма на ПЕРВОМ стыке (форы нет). Пул Deezer-аккаунтов у владельца
пустой.

Решение (владельца): тянуть следующий трек с ДРУГОГО сервиса по тому же ISRC — другой
CDN/auth, Deezer его не троттлит. Проверено end-to-end на fabric-миксе:
`Deezer трек → GET /api/gapless/altsource?service=deezer&id=<id>` (ISRC → Tidal/Qobuz
track_id, ~5с) → `_waResolveUrl` резолвит в `/api/stream/tidal-dash/<id>` → decode → 47с
буфер за ~15с (< 46с трека). Реализовано в `_waPreloadAhead` (best-effort, при неудаче
откат на Deezer в том же цикле — рабочий gapless не страдает).

**🔴 ТОЛЬКО lossless→lossless.** AAC/MP3 добавляют encoder delay (priming+padding) →
сдвиг на микросекунды → sample-accurate стык между FLAC и AAC даёт щелчок. FLAC же —
идентичный PCM без priming, а один мастер (тот же ISRC) декодится в тот же PCM на любом
сервисе → стык сэмпл-точный. Поэтому alt-источник берём в lossless или не берём вовсе.

**Две ловушки, на которых легко сделать неверный вывод:**
- `/api/stream/tidal/<id>` отдаёт JSON, а НЕ байты — реальные декодируемые байты у
  `/api/stream/tidal-dash/<id>` (same-origin концат-прокси fMP4-FLAC). CORS тут НЕ
  проблема (это через наш сервер).
- `decodeAudioData` **ДЕТАЧИТ** входной ArrayBuffer — читать `.byteLength` ПОСЛЕ decode
  вернёт 0, это не значит «пусто». Проверяй по `buffer.duration/numberOfChannels`.
- Не все сервисы несут те же сегменты: fabric-микс на Qobuz — другой эдит (24 трека vs
  37). Матчить строго по ISRC каждого сегмента, не по позиции в альбоме.
- Ограничение: если ПЕРВЫЙ трек короче ~15с — даже alt-канал не успеет; это уже предел.

## Локальный Apple-микс: ALAC НЕ декодится Web Audio → транскод в FLAC (02.08.2026)

Воспроизведение скачанного Apple-альбома/микса бесшовно из локальных файлов
(`playLocalMix` в `player_lib.js`, кнопка «▶ микс» в строке библиотеки) упирается
в то, что **Chromium/WebView2 `decodeAudioData` не декодит ALAC** — `EncodingError:
Unable to decode audio data` (проверено headless на Edge). Значит gapless-движок
`_WA` локальные `.m4a`(ALAC) НАПРЯМУЮ проиграть не может, хотя `<audio>` их тянет.

Решение (реализовано):
- `GET /api/localmix?dir=<папка>` — упорядоченные треки папки (номер из тега →
  префикс имени), у FLAC `url=/api/library/file`, у ALAC/прочего
  `url=/api/localmix/flac?p=…`.
- `GET /api/localmix/flac?p=<alac>` — ffmpeg на лету `ALAC→стерео-FLAC`
  (`-vn -map 0:a:0 -ac 2 -c:a flac -f flac pipe:1`, БЕЗ Range: WA тянет буфер
  целиком через `arrayBuffer()`). ALAC→FLAC — **lossless** (тот же PCM) → сэмпл-
  точный стык между треками микса держится. Стерео-даунмикс обязателен: Atmos-
  альбомы приходят 6-канальными 24-bit (один трек = 113МБ FLAC, а декод 6ch в
  память × look-ahead 3 = под гигабайт PCM).
- `playLocalMix` ставит `service:'local'`, `local:true`, готовый `url` → проходит
  `_waCanPlay` (для FLAC same-origin true) и переиспользует ВЕСЬ движок `_WA`
  (look-ahead, планировщик стыка) без изменений. Проверено: Taylor Swift «The Life
  of a Showgirl» (11 Atmos-треков) — `curSource=true`, часы идут, `ahead=3`.

**Гейт по длине для local.** `_waCanPlay` добавил ветку: `item.local && dur>12мин
→ false` (обычный трек 2–5 мин декодится мгновенно, а часовой DJ-микс ОДНИМ файлом
целиком в память — нельзя; длину тегов знаем всегда, длинный уходит на `<audio>`).
Транскод-эндпоинт Range не поддерживает, так что `<audio>`-фолбэк на длинном local
качает файл целиком без seek — приемлемо (это обычно и есть весь микс одним куском).

**Стартовая задержка трека 1** ~7с (транскод 226с ALAC→FLAC + фетч 41МБ + декод).
Дальше look-ahead держит фору. Для «играть пока качается + таймер до старта N сек»
(Phase 2) — отдельная задача, нужна живая Apple-загрузка для проверки.

## Кэш WebView2
Правки player.js не применяются, пока окно Ripster.exe не перезагружено ЖЁСТКО —
подними `player.js?v=` и попроси hard-reload (см. `ripster-webview-shell`).

Связано: `ripster-player-audio` (два движка, три источника звука),
`ripster-headless-verify`, `ripster-performance` (что можно/нельзя ускорить).
