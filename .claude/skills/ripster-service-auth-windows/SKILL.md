# Вход в сервис: окно в программе ИЛИ внешний браузер, с выбором

## Правило

Любой вход в аккаунт открывается **только** через `openAuthPage()` из
`static/js/service_login.js`. Никакой вход не имеет права начинаться с голого
`window.open()`.

```js
const how = await openAuthPage(url, 'Название сервиса');   // 'here'|'external'|'copy'|null
if (how === 'here') return;                 // мы уходим со страницы, ждать нечего
if (!how) { /* человек отменил — погасить helper */ return; }
// 'external' | 'copy' — helper жив, ждём колбэка
```

Диалог даёт три способа, и каждый из них рабочий:

| Вариант | Что делает | Когда единственный рабочий |
|---|---|---|
| **Прямо здесь** | `location.href = url` в том же окне | Ripster.exe / жёсткий блокировщик попапов — заблокировать переход нечем |
| **Во внешнем браузере** | сервер открывает системный браузер (`/api/open-url`) | нужен настоящий браузер: букмарклет, панель закладок, вход через менеджер паролей |
| **Скопировать ссылку** | ссылка в буфер | Ripster открыт через туннель с другой машины — сервер физически не может открыть браузер человека |

`opts.here === false` убирает первый вариант. Ставить его там, где **уход со
страницы теряет то, что показано в самом Ripster**:

- device-flow (Tidal TV, Яндекс) — код подтверждения нарисован в Ripster;
- Яндекс implicit-OAuth — токен возвращается во фрагменте адреса и его надо
  вставить обратно в поле здесь;
- `/apple/login` — там букмарклет, который надо перетащить на панель закладок,
  а в WebView2 её нет и назад вернуться нечем.

## Почему именно так (31.07.2026, два пользователя)

WebView2 без обработчика `NewWindowRequested` **не открывает попапы вообще** и
возвращает `null` — ровно то же, что делает блокировщик в браузере. Отличить
нельзя. Поэтому:

- фронт писал «попап заблокирован — разреши попапы», человек разрешал, ничего не
  менялось: разрешать было нечего;
- хуже, ветка «попап не открылся» ещё и дёргала `login-cancel`, убивая helper,
  который слушал порт колбэка → вторая жалоба, `ERR_CONNECTION_REFUSED` на
  `127.0.0.1:4381`, выглядела как совсем другой баг.

Диагностический признак: **«из браузерного ярлыка работает, из Ripster.exe нет»**
— это почти всегда WebView2, а не логика. Первым делом спрашивать, чем запускали.

## Вторая половина правила: вернуть человека обратно

Вход не считается сделанным, пока Ripster сам не увидел новый статус. Обязательно:

1. **Страница колбэка helper'а возвращает браузер в Ripster.** Helper получает
   адрес через переменную окружения `RIPSTER_RETURN_URL` (её ставит
   `ripster/routes/core.py::_return_url()`, учитывает `RIPSTER_PORT`), отдаёт
   страницу на русском и делает `<meta http-equiv="refresh">` на
   `http://127.0.0.1:<порт>/?spotify_login=ok`.
   Без этого при варианте «прямо здесь» возвращаться просто некуда, а `window.close()`
   не работает: закрыть можно только вкладку, которую открыл скрипт, а с попапами
   мы как раз и распрощались.
2. **Фронт перепроверяет статус на возврате**, а не только по WebSocket-событию.
   Событие уходит в никуда, если человек за это время перезагрузил страницу или
   логинился в другой вкладке — и тогда Ripster показывает «не авторизован» до
   ПЕРЕЗАПУСКА ПРИЛОЖЕНИЯ. Именно так это и выглядело у пользователя. Обработчик
   возврата живёт в конце `static/js/auth_ui.js` (`_spotifyLoginReturn`).
3. **Опрос статуса параллельно событию.** `orpheusLogin()` опрашивает
   `/api/orpheus/status` раз в 2.5 с до таймаута — событие лишь ускоряет.

## Серверная часть — узко

`/api/open-url` и `/api/orpheus/login-open`:

- открывают **только** URL, который сервер сам сгенерировал (хранится в глобале
  модуля), никогда присланный клиентом — иначе это «открой что угодно на машине
  хозяина»;
- только при `request.client.host in ("127.0.0.1", "::1", "localhost")`;
- только `http/https` (`file:` и протокольные ссылки запускают посторонние программы);
- `webbrowser.open` в `asyncio.to_thread`, запасной путь `os.startfile`.

Если оба способа не сработали — `openExternal()` кладёт ссылку в буфер и
показывает её. Тупика быть не должно никогда.

## Проверять перед релизом

1. Прогнать вход **в `Ripster.exe`**, а не только в браузере.
2. Серверную часть — юнит-тестом с подменённым `webbrowser.open`, без реально
   открывающихся окон (хозяин часто в игре, фокус красть нельзя).
3. Живьём: helper реально слушает свой порт (4381 / 5588) **и** отмена его гасит.
4. Убедиться, что после входа статус в UI меняется **без перезапуска приложения**.

Связано: скиллы `ripster-webview-shell` (что ещё ломается в WebView2),
`ripster-headless-verify` (как это проверять), `ripster-spotify-tokens`.
