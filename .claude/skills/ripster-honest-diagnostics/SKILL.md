# Когда врёт прибор, а не двигатель

Самая дорогая категория времени в этом проекте — не сами поломки, а **часы,
потраченные на неверную причину, потому что инструмент диагностики показал не
то**. Ниже пять способов, которыми это уже происходило. Все реальные.

## 1. Проверка нашла проблему и умерла, печатая её

`tools/check_js_collisions.py` находил три реальных дефекта зеркала — и падал с
`UnicodeEncodeError` на строке `print("  ✗ " + line)`, потому что консоль
Windows в cp1251. В выводе оставался трейсбек, а находки не появлялись **вообще**.
Выглядело как «сломанный скрипт», лечилось как «сломанный скрипт».

```python
# Первое, что делает любой наш инструмент с текстовым выводом:
for stream in (sys.stdout, sys.stderr):
    try: stream.reconfigure(encoding="utf-8", errors="replace")
    except Exception: pass
```

Правило: **инструмент, который не может напечатать свою находку, хуже
отсутствующего** — отсутствующий хотя бы не создаёт ложного спокойствия.

## 2. Программа провалилась, но вернула код успеха

Живой случай 08.08.2026. Go-загрузчик печатает:

```
Failed to get album response.
ERROR Failed to rip album: error getting album response
```

…и **выходит с кодом 0**. Обёртка смотрит только на код возврата, не находит в
нём ошибки, но и успеха не видит — и выдаёт человеку `✗ Exit code 0`. Сообщение
бессмысленное: нулевой код означает успех. Настоящая причина (релиз есть только
в индийском магазине Apple) в этот момент лежала строкой выше в логе.

Правило: **код возврата — не единственный источник правды**. Если внешний
инструмент умеет провалиться с нулём, разбирать надо его вывод, а сообщение
человеку строить из разобранного, а не из кода. И никогда не показывать
пользователю строку вида «Exit code N» как причину — это признание, что причину
не разобрали.

## 3. Одно сообщение на три разные причины

`«Failed to get album»` у Apple означало (в разное время) минимум три вещи:
протух regex скрапера токена, нет прав в регионе, релиза нет в этом магазине.
`«не нашёл пакет ripster»` означало отсутствие пакета, отсутствие зависимости
И несовпадение регистра папки — а настоящее исключение при этом проглатывалось.

Правило: **сообщение обязано различать причины, иначе оно не сообщение, а шум.**
Прежде чем добавить обработчик с человеческим текстом, спроси: сколько разных
состояний мира приводят сюда? Если больше одного — либо разделяй, либо вкладывай
исходную ошибку целиком.

## 4. Читатель глушит исключение и тихо выключает подсистему

BOM в начале `tgbot/config.json` (наследие записи из PowerShell) **молча**
выключил три подсистемы разом: отчёт владельцу, проверку зависания Bot API и
телеметрию. Все три читателя ловили `except` без разбора и продолжали с пустым
конфигом. По логам это неотличимо от «нечего было отправлять».

Правило: `except Exception: pass` вокруг чтения конфигурации — **выключатель
подсистемы**, а не защита. Если конфиг не прочитался, это должно быть видно.
Читать текстовые конфиги как `utf-8-sig`, писать — только из Python.

## 5. Детерминированный отказ повторяют, как временный

Тот же случай 08.08: 404 «релиза нет в этом магазине» ушёл в авто-повтор
**трижды** с паузами 15/45/120 секунд. Три с половиной минуты человек ждал
повторения заведомо того же ответа, и всё это время интерфейс говорил
«повтор 1/3», то есть «скорее всего сейчас получится».

Правило: повтор осмыслен для **временных** отказов (сеть, 5xx, троттлинг). Для
404, 401, «нет прав», «нет в каталоге» повтор — это ложное обещание. Разделяй
классы отказов до того, как включать backoff.

## Как этим пользоваться

Когда что-то «не работает, а почему — непонятно», сначала проверь **сам прибор**:

1. Инструмент вообще допечатал свой вывод до конца, или упал на середине?
2. Сообщение построено из разобранной причины или из кода возврата/шаблона?
3. Сколько разных состояний мира дают ровно это сообщение?
4. Нет ли по пути `except`, который превращает «сломалось» в «пусто»?
5. Мы повторяем то, что имеет шанс измениться, или молотим в стену?

И обратное правило, для своего кода: **любая новая проверка обязана уметь
рассказать о своей находке** — в правильной кодировке, с разделением причин, с
исходной ошибкой внутри. Проверка, которая при поломке выглядит так же, как
проверка при успехе, не нужна.

Связано: скиллы `ripster-autoheal` (что чинится само), `preflight-ripster`
(гейты перед сборкой), `ripster-frontend-file-drift` (там же — сканер, который
теперь умеет печатать свои находки).
