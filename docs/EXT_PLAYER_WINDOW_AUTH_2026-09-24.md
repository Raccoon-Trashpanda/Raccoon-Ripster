# Внешнее окно плеера: допуск и проверка НАСТОЯЩИМ окном (24.09.2026)

## Корень: почему окно было мертво при зелёных вкладках

Окно «Внешний плеер» — отдельный процесс `python -m ripster.player_window`
(pywebview/WebView2) со СВОИМ профилем браузера. Хозяйская кука
`ripster-session` в нём есть не всегда — а без неё рукопожатие `/ws`
отвергается: `ripster.auth.ws_allowed` → HTTP 403 при апгрейде. Окно не
регистрировалось панелью в `ripster.rp_relay` и не видело состояние:
«живёт своей жизнью».

Измерено стендом (s1, прогон 7): `ws://127.0.0.1:7805/ws` без куки —
`403 Forbidden`; с хозяйской — принят, первый кадр `type=init`.

Почему прежняя проверка (s1–s6, вкладки браузера) этого не поймала: вкладки
делят куку одного браузера, а окно — нет. Вкладки доказали протокол релея,
но не факт допуска окна.

## Поток допуска (реализация)

1. **Выпуск.** `POST /api/player-window/open` (только хозяин) просит
   `ripster.launch_token.mint()`: 32 байта `secrets.token_hex`, TTL 60 с,
   в памяти сервера — только SHA-256, потолок незакрытых выпусков 32.
2. **Передача.** Токен едет окну во **фрагменте** адреса
   (`/static/panel/index.html?transport=relay#launch=<t>`): фрагмент не
   уходит на сервер — ни в access-лог, ни в Referer. Живому окну свежий
   пропуск передаёт файл-флаг `logs/player_window.launch` (страница не
   перезагружается: окно само зовёт `window.rpClaim`).
3. **Обмен.** Панель при boot зовёт `POST /api/player-window/claim {token}`
   (путь — в публичном allowlist, допуск держится на токене, не на анонимности):
   403 — не loopback-адрес; 401 — нет/не наш/просрочен/истрачен (не
   различаются, чтобы не подсказывать атакующему). Успех — обычная хозяйская
   кука (`HttpOnly`, `SameSite=Strict`, `Secure` при https), после чего
   панель стирает токен из адреса (`history.replaceState`).
4. **Постоянство.** Окно живёт в постоянном профиле `player_window_profile`
   — кука переживает перезакрытие окна. Истекла — панель поднимает флаг
   `player_window.reauth`, серверный сторож (`start_reauth_watcher`, заведён
   из `lifespan` app.py:822 — на `on_startup` в этом приложении не звучит)
   выпускает новый пропуск тому же живому окну.
5. **Диагностика.** `GET /api/player-window/relay-status` (только хозяин):
   hosts/panels/active_host/playing + последний ack панели: title, have,
   live/nolink (глазами самой панели) и keys/cmds (сколько Space панель
   получила и сколько команд послала).

Правила безопасности проверены тестами `tests/test_player_window_auth.py`
(31 тест, зелёные): однократность (включая гонку), срок, мусор/неизвестный
токен, не-loopback → 403, повтор/просрочка → 401, `/ws` с выданной кукой —
принят / без неё — 403, relay-status — только хозяин, провод сторожа в
lifespan проверяется статически (урок «написано и не вызвано»).

## Лаунчерово окно (oswin): общий вопрос проверен

Профиль WebView2 лаунчера (`%LOCALAPPDATA%\Ripster\webview`, постоянный,
`private_mode=False`) — отдельный от браузера владельца, и куки в нём
измеренно НЕТ (база `EBWebView\Default\Network\Cookies` — 0 строк). Окна
лаунчера это не ломает:

- главное окно лаунчера показывает страницу входа и после логина держит
  сессию в своём профиле (как любой браузер);
- панельное окно лаунчера грузится с `?rpwin=1` — состояние идёт через
  pywebview-мост (`js_api`), а не через `/ws`-релей, хозяйская кука панели
  для этого не нужна; `/ws` в этом окне не задаёт доступ (ретраи с backoff,
  banner-сторож RELAY-режима туда не заглядывает).

Разовый пропуск нужен именно standalone-окну с `transport=relay` — его он и
получает.

## Реальный стенд: `tools/panel_window_auth_check.py` (обязательная проверка)

Запасной порт 7805, боевой 7799 не тронут. Хост — headless-вкладка через
`tools/headless_reaper` (профиль с меткой, снос дерева в finally); окно —
НАСТОЯЩЕЕ `python -m ripster.player_window`, видно на время прогона, в
конце закрыто. Измерение клавиатуры: после ложных CDP-порт «успехов» (порт
9441 принадлежал Edge владельца) стенд меряет не «нажатие», а последствия:
DOM вкладки-хоста + heartbeat хоста из relay-status + самоотчёт панели.

Дефекты, найденные ТОЛЬКО настоящим окном (вкладками не виделись):
1. окно заводило ДВА сокета `/ws` (panels=2) — `connectWS()` теперь
   идемпотентен (живой Connecting/Open сокет не дублируется);
2. `win.close()` у pywebview-окна нет — флаг закрытия падал в AttributeError
   и окно выживало; зовётся `destroy()`;
3. доставка OS-клавиш в WebView2 из автотестa дрожит: `keybd_event` при
   подтверждённом переднем плане и фокусе контента в прогонах 3–6 не доходил
   до DOM (в прогоне 2 — доходил). Стенд добавляет путь POST-сообщений:
   клик по пустому месту шапки (забирает DOM-фокус из автофокусного поля,
   как делает человек) и `WM_KEYDOWN/WM_KEYUP` в очередь окна контента.
   Для человека за рулём это не дефект продукта: живая мышь и живая клавиша
   идут обычным путём; доказывается лишь двусторонность моста.
